# RepoOps 优化复测结论

更新日期：2026-08-01。

## 当前可对外使用的结果

以完整、无状态污染、逐任务 pre-fix 的跨语言 v4 为正式结果：

| 指标 | RepoOps v4 | Claude Code v1 |
|---|---:|---:|
| 任务 | 15 | 15 |
| 结构化成功 | **15/15** | 13/15 |
| 分类准确率 | **100.0%** | 86.7% |
| File Recall@5 | **93.1%** | 77.1% |
| 调查调用 | **137** | 220 |
| Invalid Call Rate | **0.73%** | 5.45% |
| 引用幻觉率 | **0%** | 4.46% |
| Runner-reported tokens | **1,881,777** | 2,424,549 |
| 累计逐题耗时 | **1,886.8 秒** | 2,066.4 秒 |

RepoOps 比 Claude Code 多完成 2 条，分类高 13.3 个百分点、File Recall@5 高 16.0 个
百分点，调用少 37.7%、tokens 少 22.4%、累计耗时少 8.7%。这是当前 README、项目
报告和简历统一使用的口径。

原始证据：

- `eval/runs/deepseek-v4-pro-cross-language-repoops-v4/`
- `eval/runs/deepseek-v4-pro-cross-language-claude-code-v1/`
- `eval/runs/deepseek-v4-pro-cross-language-comparison-v2.json`

## 本轮优化

- Provider 对短暂响应解析失败做有限重试，并恢复可识别的 DSML 序列化工具参数；
- workspace 检索按唯一路径聚合，补充稀有查询词覆盖，减少单文件 chunk 挤占 top-k；
- 搜索结果在字符预算内始终保持有效 JSON；
- 固定历史 benchmark 可从受控本地 worktree 读取 pinned SHA 文件，避免网络依赖；
- prompt 携带任务集已有 Issue 标题，并明确 bug/feature 分类边界；
- 对同一文件重复精确读取节流；
- 已有工具证据但主循环报错时，改用有界工具证据做两次紧凑最终化。

## 为什么没有继续使用 Python 压力 run

Python v5 完成 20/20 结构化输出，证明紧凑最终化改善了“有证据但无最终 JSON”的
问题；但 GitHub Issue API 被网络策略阻断时，旧 prompt 没有携带标题，6 条任务的
分类/搜索发生漂移，最终分类 70.0%、File Recall@5 73.7%。修复后，这 6 条目标回归
均得到正确分类，但目标回归不能代替完整、一次性全量 benchmark。

v6 和 v7 用于继续施压 endpoint 收尾可靠性。v6 未完成；v7 在用户决定停止时只有
18/20 shard 产生汇总，其中 15 条成功、3 条因 endpoint 连接失败无最终答案，另 2 条
尚未运行完成。两轮都不具备完整分母，明确排除在正式指标和简历之外。

## 简历口径

> 构建 Python / Go / TypeScript / Rust 四仓库真实历史 Issue 评测集；用 DeepSeek
> V4 Pro 在 15 条逐任务 pre-fix 跨语言任务上取得 15/15 结构化成功、100.0% 分类和
> 93.1% File Recall@5，同主模型 Claude Code 为 13/15、86.7% 和 77.1%，调查调用
> 减少 37.7%；完整保留失败、污染和中止 run 审计。

## 仍需主动披露的边界

- 跨语言集只有 3 个仓库、每仓 5 条、一次模型采样；
- 对照控制了主模型、任务、SHA 和评分器，但两套 Agent 的系统提示、工具协议不同；
- 代码是 pre-fix 快照，GitHub Issue 当前评论不是历史时间切片；
- File Recall@5 是对人工核心文件的宏平均，不等价于补丁正确率或根因完全正确；
- Runner-reported token 口径依赖两个运行时各自上报，只适合本轮工程对照。

因此可以说“在本轮受控任务上明显优于 Claude Code”，不应说“全面击败 Claude Code”
或“跨语言生产准确率 100%”。
