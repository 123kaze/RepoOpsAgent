# RepoOps 优化复测结论

更新日期：2026-08-01。

## 当前可对外使用的结果

v4 是完整、无状态污染、逐任务 pre-fix 的锁定高点；新增原生消融和重复 run 后，
必须一起披露：

| 系统 / run | 结构化成功 | 分类 | File Recall@5 | 调用 | Tokens |
|---|---:|---:|---:|---:|---:|
| RepoOps v4（锁定完整 run） | **15/15** | **100.0%** | **93.1%** | 137 | 1,881,777 |
| RepoOps 前原生 nanobot | **15/15** | **100.0%** | 90.4% | **136** | **1,354,894** |
| 原生 + GitHub MCP v1.0.5 | **15/15** | **100.0%** | 90.4% | 155 | 1,497,269 |
| Claude Code v1 | 13/15 | 86.7% | 77.1% | 220 | 2,424,549 |
| RepoOps v5（同日重复 run） | 10/15 | 66.7% | 59.6% | 162 | 1,893,061 |

RepoOps v4 比 Claude Code 多完成 2 条，File Recall@5 高 16.0 个百分点、调用少
37.7%、tokens 少 22.4%。但相对原生 nanobot 只高 2.7 个百分点，调用基本持平、
tokens 多 38.9%；增益全部来自一条 5 文件 TypeScript feature。v5 又有 5 条结构化
收尾失败，因此 README 和面试应把 93.1% 说成“一次锁定 run”，不能说成稳定准确率。

## 本轮优化

- Provider 对短暂响应解析失败做有限重试，并恢复可识别的 DSML 序列化工具参数；
- workspace 检索按唯一路径聚合，补充稀有查询词覆盖，减少单文件 chunk 挤占 top-k；
- 搜索结果在字符预算内始终保持有效 JSON；
- 固定历史 benchmark 可从受控本地 worktree 读取 pinned SHA 文件，避免网络依赖；
- prompt 携带任务集已有 Issue 标题，并明确 bug/feature 分类边界；
- 对同一文件重复精确读取节流；
- 已有工具证据但主循环报错时，改用有界工具证据做两次紧凑最终化。

## 为什么没有继续使用 Python 压力 run

Python v5 完成 20/20 结构化输出，证明紧凑最终化改善了“有证据但无最终 JSON”的
问题；但 GitHub Issue API 被网络策略阻断时，旧 prompt 没有携带标题，6 条任务的
分类/搜索发生漂移，最终分类 70.0%、File Recall@5 73.7%。修复后，这 6 条目标回归
均得到正确分类，但目标回归不能代替完整、一次性全量 benchmark。

v6 和 v7 用于继续施压 endpoint 收尾可靠性。v6 未完成；v7 在用户决定停止时只有
18/20 shard 产生汇总，其中 15 条成功、3 条因 endpoint 连接失败无最终答案，另 2 条
尚未运行完成。两轮都不具备完整分母，明确排除在正式指标和简历之外。

本轮跨语言 v5 是完整 15 条重复 run，不因结果较差而排除：10/15 成功，5 条在
`tool_budget_exhausted` 后没有合法 JSON。它证明当前紧凑最终化仍不能保证每次收尾。

## 简历口径

> 构建 Python / Go / TypeScript / Rust 四仓库真实历史 Issue 评测集；用 DeepSeek
> V4 Pro 在 15 条逐任务 pre-fix 跨语言任务上取得 15/15 结构化成功、100.0% 分类和
> 93.1% File Recall@5，同主模型 Claude Code 为 13/15、86.7% 和 77.1%，调查调用
> 减少 37.7%；另以 RepoOps 前原生 nanobot 和官方 GitHub MCP 做消融，并完整保留
> 失败、污染、重复和中止 run 审计。

若面试官追问基线，必须补充：原生 nanobot 是 15/15、100.0%、90.4%；RepoOps v5
重复 run 是 10/15。不要用 Claude Code 的 16.0pp 差距回答“相对 nanobot 提升多少”。

## 仍需主动披露的边界

- 跨语言集只有 3 个仓库、每仓 5 条；v4、原生、MCP 各只有一次全量采样；
- 对照控制了主模型、任务、SHA 和评分器，但各系统的提示、工具协议不同；
- 代码是 pre-fix 快照，GitHub Issue 当前评论不是历史时间切片；
- File Recall@5 是对人工核心文件的宏平均，不等价于补丁正确率或根因完全正确；
- Runner-reported token 口径依赖两个运行时各自上报，只适合本轮工程对照。

因此可以说“RepoOps v4 在本轮受控任务上优于 Claude Code，并在复杂多文件 feature
上比原生 nanobot 多召回”，不应说“全面击败同类工具”“原生 nanobot 不会做”或
“跨语言生产准确率 100%”。
