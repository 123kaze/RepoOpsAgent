# RepoOps 实现记录

## 目标与边界

本次工作把 nanobot 特化为 RepoOps，同时遵守“核心保持小、能力从边缘扩展”的
约束。`agent/loop.py`、消息总线、Provider、会话、Cron、Gateway 和 WebUI 数据流
均未加入 RepoOps 分支；`agent/runner.py` 只补了通用的临时 `model_messages` Hook
扩展点，不包含 Issue/PR/CI 领域判断。

## 已完成

工具通过 nanobot 的自动发现和 `ToolRegistry` 注册，无需修改 Runner。

### 2. GitHub API 与安全

- 固定相对 API 路径并限制在配置的 HTTPS origin。
- 每个请求经过 nanobot 共享 SSRF guard。
- Actions 日志 302 只允许 GitHub 签名下载域名，并逐跳重验。
- 下载压缩包与展开内容都有大小上限。
- GitHub 输出统一标记为不可信外部内容。
- 仓库 allowlist 默认拒绝全部。

GitHub REST 契约按 2026-03-10 版本头调用；Issue、PR 与 Actions 端点按 GitHub
官方文档核对。

### 3. 结构化任务状态

新增 `RepoTaskState`、`Evidence`、`Hypothesis` 和 `ToolRecord`。每个任务独立保存：

- 已确认事实
- 缺失信息
- 相关文件与 Issue
- 带置信度和证伪方式的假设
- claim-to-source 证据
- 工具轨迹与下一步
- 已完成动作（与开放的 `next_actions` 共同形成 TODO 进度）
- 是否需要人工批准

状态存储在活动工作区 `.repoops/` 内，使用临时文件、`fsync` 和原子替换。

### 4. Agent Status Bar

新增 `nanobot/agent/hooks/repoops_status.py`。每个 RepoOps turn 创建独立 Hook，从工具
生命周期和任务/草稿 store 计算：

- 当前 iteration 与上限；
- 已用/剩余工具预算；
- `工具名 + 规范化参数` 的 SHA-256 短指纹及重复次数；
- 总错误与连续错误；
- 持久证据、唯一工具结果和最近三次证据增量；
- facts、hypotheses、开放/完成 TODO 和当前动作；
- 当前 session 的待审批草稿。

Runner 在上下文治理后显式复制模型消息列表，Hook 只向该副本追加 runtime status；
原始 `messages` 不变。相同指纹达到 3 次、连续 3 次无新增证据、剩余预算不超过
2 次、存在待审批时，状态栏分别要求换查询/结束、换策略/结束、立即整理结论、禁止
继续写入。参数只显示脱敏后的 hash；`current_action` 有长度上限并 JSON 转义。

该机制是运行时决策控制，不冒充硬调度器。模型仍可能忽略预算；GitHub 写操作安全
继续由审批状态机强制执行。详见 [Agent 状态栏设计与验证报告](Agent状态栏设计与验证报告.md)。

### 5. 人工审批

写操作分成草稿和执行两个工具。执行条件同时包括：

- 草稿仍为 pending；
- 仓库仍在 allowlist；
- 同一个 session；
- 不同 turn；
- 原始用户文本中存在独立一行的精确批准口令；
- 已配置 GitHub token。

执行前原子抢占为 `executing`，成功后标记 `executed`。遇到不确定的网络失败时
不自动退回 pending，避免重复 GitHub 写入。

### 6. RAG / 检索

- Python 顶层函数与类的 AST 分块
- 覆盖模块级代码的重叠行窗口
- BM25 关键词检索
- 本地 trigram 相似度
- 精确符号/路径 boost
- 依赖、构建产物、`.git`、`.repoops`、`.nanobot` 和 `sessions` 排除

该实现可离线复现，不依赖外部 embedding。它是“符号优先混合检索”MVP，不冒充
已经完成外部 dense embedding 或 cross-encoder。

### 7. Skill 与自动化

- always-on `repoops` 总体策略
- `repoops-issue-analysis`
- `repoops-pr-review`
- `repoops-ci-diagnosis`
- 可由 nanobot Cron 调用的只读日报工具

### 8. 评测

原来的 20 条自造离线任务已全部替换为 `HKUDS/nanobot` 的真实历史 Issue。每条
任务包含公开 Issue URL、合并 PR、固定 commit SHA 与人工筛选的核心生产文件。

新增：

- `nanobot.repoops.benchmark`：通过 `Nanobot.from_config().run_streamed()` 启动
  RepoOps Agent，记录工具名、脱敏参数、状态、完整有界结果、hash、耗时、最终
  JSON 和 usage，不保存隐藏 reasoning；
- `nanobot.repoops.benchmark_merge`：合并并行 shards 并重新计算确定性指标；
- `nanobot.repoops.cross_language_benchmark`：按任务仓库和 SHA 准备独立 pre-fix
  worktree，并统一编排 RepoOps、Claude Code、RepoOps 前 nanobot 与 GitHub MCP
  多仓库运行；
- `nanobot.repoops.cross_language_report`：生成总体、分语言、分仓库以及成功样本条件
  指标的机器可读对照；
- `nanobot.repoops.claude_benchmark`：以无交互、无项目记忆的 Claude Code CLI 运行
  同任务和同主模型，并把 Bash/Read 调查轨迹归一化给统一评分器；
- `nanobot.repoops.generic_benchmark` 与 `scripts/pre_repoops_benchmark_worker.py`：
  把 RepoOps 父提交放在子进程 `PYTHONPATH` 首位，用旧 `Nanobot.run_streamed()` 运行
  通用工具或官方 GitHub MCP，并生成相同 trajectory/prediction；
- `eval/demo_cases.json`：3 Issue、3 PR、3 个真实失败 Actions run；
- `eval/demo_ground_truth.json`：与 Agent prompt 分离的人工标准答案；
- `eval/deepseek_config.example.json`：不含明文 key 的 DeepSeek V4 Pro 配置；
- invocation 级 session namespace 与 state directory 隔离，避免旧答案污染；
- 对常见模型 JSON 小错误做可重复 repair，再用 Pydantic schema 校验。
- 参数按敏感键脱敏；非结构化工具输出、错误与最终答案额外过滤常见 API key、
  GitHub token 和 Bearer credential，并对脱敏后的结果重新计算 hash。

10 项指标覆盖分类、File Recall@5、工具准确性、无效/重复调用、证据完整率、引用
可追溯失败率、审批命中率和平均步骤数。citation 只有在工具结果中能找到 source
且 excerpt 达到保守 token overlap 时才算受支持。
无效工具调用只统计真实 tool error/参数错误，不把“最终答案不可解析”混进
Invalid Call Rate；正式基线纠正后为 21/222（9.5%）。

首次真实 smoke 揭示了 25 步过度检索问题；加入 8 次工具调用/5 批次的 prompt
预算并隔离会话后，同题降为 8 步。优化前后轨迹均保留在 `eval/runs/`。

正式 DeepSeek V4 Pro 基线完成 20/20 条执行，17 条得到可解析 JSON；分类准确率
80.0%、File Recall@5 75.3%、平均 11.1 步。3 条达到迭代上限后未完成结构化收尾，
均作为失败进入正式指标。

修复后首次报告的 Python v2 读取了这轮 baseline 留下的 task state，因此 20/20、
95.0% 分类和 85.3% File Recall 全部撤回。重绑 store 并用全新 worktree 运行的 v3
为 18/20、85.0%、77.0%，197 次调用；相对 baseline 调用少 11.3%，但 tokens 多
6.0%。两条失败和 3 次无效 state update 都保留在正式轨迹中。

面试演示集完成 3 Issue、3 PR、3 个指定 CI job，9/9 得到可解析报告，共 78 次
RepoOps 工具调用。CI 摘要器改为优先 timeout、pytest、Ruff rule 等强因果信号，
避免 setup 日志中的 `ErrorActionPreference` 抢占输出预算。

跨语言任务集新增 Cobra（Go）、Vitest（TypeScript）、bat（Rust）各 5 条真实 Issue，
每题固定 closing PR 第一父提交的 pre-fix SHA。首次实跑发现本地检索虽在 pre-fix
worktree，远程 `repoops_read_file` 默认 ref 仍可能落到 GitHub `HEAD`；第二轮虽钉住
SHA，但已构造的 `RepoTaskStore` 没有随 config 的 `state_dir` 变化而重建，仍读取了
第一轮 state。两轮均完整保留并标为无效。

最终修复同时把每个 RepoOps tool 的 `pinned_read_ref` 硬钉到任务 SHA、注销无法查询
历史提交的远程 Code Search，并把 task/draft store 重新绑定到 invocation UUID。
回归测试覆盖主动传 `HEAD`、单 invocation 混入多个 SHA、旧 state 隔离和跨仓库编排。

在 v3 失败分析后又增加 Provider 短暂解析失败重试、可识别 DSML 参数恢复、检索结果
按唯一路径去重与稀有查询词覆盖、有效 JSON/top-k 输出和重复文件读取节流。正式跨
语言 v4 中，RepoOps 与 Claude Code 分别为 15/15 与 13/15 结构化成功，全量分类
100.0% vs 86.7%，File Recall@5 93.1% vs 77.1%，调查调用 137 vs 220。该结果单列，
未与旧 Python 20 条混算。

进一步用 RepoOps 首次实现的父提交 `6a1a45d0` 做消融：原生 nanobot 与原生加官方
GitHub MCP v1.0.5 均为 15/15、100.0% 分类、90.4% File Recall@5。RepoOps v4 的
2.7pp 召回增益全部来自一条 5 文件 TypeScript feature，但 tokens 比原生多 38.9%。
同日 RepoOps v5 完整重复 run 只有 10/15，5 条在 tool budget 用尽后没有合法 JSON，
因此文档同时报告高点与重复性失败。

后续还实现了固定历史快照的本地精确读取、Issue 标题随任务 prompt 传入、分类边界
约束、紧凑最终化和已有工具证据下的错误恢复。Python v5 达到 20/20 结构化成功，但
网络阻断时遗漏标题导致分类漂移；修复后的 6/6 目标回归仅作为缺陷验证。v6/v7 压力
实验未完成，不进入正式指标。
